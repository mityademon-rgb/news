# TIMECODE — обязательный навык оператора сайта

## 0. Вход без повторных вопросов
Если пользователь просит «поменяй на сайте», «урок», «опубликуй», «TIMECODE», «исправь», действуй здесь. Не проси пользователя копировать код и не предполагай, что commit означает публикацию. Главный документ: `PROJECT_AI_HANDBOOK.md`, история: `PROJECT_CHANGELOG.md`, инструкции: `AGENTS.md`. Прочитай их прежде, чем менять код. Ответы пользователю краткие и по делу.

## 1. Проверенная карта
- Сайт: https://timecode-lab.ru ; на 2026-10-16 DNS A timecode-lab.ru и www.timecode-lab.ru = 217.149.24.234 (всегда перепроверить).
- GitHub: `mityademon-rgb/news`, **только ветка `boom-kadr-deploy`**, НЕ main (main — другой проект).
- Static production: `/var/www/boom-kadr` на доступном через `amsterdam_*` сервере. Основной CRM/server доступ — `producer_server_*`; адреса серверов читай по /var/www/ptk-crm/RUNBOOK.md.
- Источники: `lessons.js` (сцены и каталог), `lesson-plans.js` (преподаватель), `app.js` (SPA), `index.html` (подключение), `styles.css`, `assets/`.
- **`site.js` только генерировать** командой `bash scripts/build-site.sh`, результат обязан равняться `lessons.js + lesson-plans.js + app.js`.
- Hash routes `#/lesson/<id>`, каталог на главной по якорю `#lessons`. Проверяй фактическую карточку, вход в урок, листание сцен и медиа, а не только 200 OK.

## 2. Уроки, порядок и уникальность
- KIDS LAB: исходные уроки 01–09; добавленные уроки «Звук в кино» №10 (`kids-film-sound`), «Звук на ТВ» №11 (`kids-tv-sound`).
- MEDIA LAB: исходные уроки A01–A06; «Звук в кино» A07 (`adult-film-sound`), «Звук на ТВ» A08 (`adult-tv-sound`).
- Перед изменением считать все `number` и `id` отдельно для tracks `kids` и `adult`: запрет повторов, сортировка численно (A01 до A08). Не помещать новые уроки в начало визуального каталога.
- Кнопки/игры и преподавательские материалы не должны ломаться. Teacher scripts только в teacher mode; помни, что localStorage gate не является защищённой авторизацией.
- Задания должны быть конкретными и пригодными для проведения учениками. Для мультимедийного урока обязательно **реальные проверенные изображения, звуки и видео**, а не текст «покажите видео». Проверяй URL, лицензии и воспроизведение в браузере; браузерные синтезированные звуки так и маркируй.

## 3. Правильный цикл публикации
1. Прочесть handbook/changelog и статус GitHub branch/commit, сравнить с живыми файлами: не переписывать чужие изменения.
2. Править исходники `lessons.js`, `lesson-plans.js`, `app.js` и `assets`, а не только bundle. Делать резервные копии до любых production правок.
3. Собрать `site.js` и проверить точное равенство канонической конкатенации (в том числе переносы и конечные newline).
4. `node --check` для JS, `bash scripts/build-site.sh --check`; проверить уникальность `id`/номеров и структуру сцен, синтаксис.
5. Обновить версию `site.js?v=...` в `index.html` для обхода 7-дневного cache; внести запись в `PROJECT_CHANGELOG.md`, при изменении инфраструктуры и в `PROJECT_AI_HANDBOOK.md`.
6. Commit только в `boom-kadr-deploy`. Публикация выполняется workflow `.github/workflows/deploy-boom-kadr.yml` (push с отслеживаемыми путями); убедиться в успешном run, не просто созданном коммите.
7. После деплоя сверить production `index.html`, `site.js`, исходники и git-версию; проверить HTTPS и `#/lesson/<id>` через реальный браузер и наличие карточек/плееров.
8. Если отсутствует браузерное подтверждение, явно так и сообщить. Никаких «готово» по одному HTTP 200.

## 4. Публикация и внешние процессы
- Рабочий workflow распаковывает сайт на сервер и **переустанавливает nginx config**. Поэтому ручные изменения `/etc/nginx/conf.d/boom-kadr.conf` и `/var/www/boom-kadr/index.html` могут быть затёрты при следующем GitHub Actions.
- Перед вмешательством в nginx проверить `.deploy/boom-kadr-http.conf`, `.deploy/boom-kadr-https.conf` и реальный `nginx -T`; не ломать существующее /tc/ proxy и соседние сайты.
- В workflow присутствуют шаги сертификата и DNS; проверяй целесообразность изменения workflow перед деплоем, не трогай DNS без прямого поручения.
- Если server exec обладает read-only ограничением — строго его соблюдай. Используй только явно разрешённые операции и репозиторный deploy. Не обходи запреты.
- Проблемы SSR/кеша: сначала сравни HTML и JS реально обслуживаемых через сеть, затем вывод браузера и только после — правки. Если коллега параллельно деплоит, не перезатирай.

## 5. TLS: что было обнаружено 16.10.2026
- `217.149.24.234:443` с SNI `timecode-lab.ru` отдавал действующий сертификат Let's Encrypt CN=timecode-lab.ru, NotAfter 2026-12-16.
- `217.149.24.242:443` с тем же SNI отдавал **чужой сертификат CN=amd.com**, вызывая `ERR_CERT_COMMON_NAME_INVALID` при попадании на этот IP.
- На момент диагностики A-записи домена указывали на .234, но клиент жаловался на нерегулярную ошибку. Это **не доказывает**, что проблема решена: выяснить клиентский IP назначения, proxy/VPN/кеш DNS и stream multiplexor для .242, затем чинить только подтверждённую причину.
- Не перевыпускай сертификат, если он действителен. Никогда не рекомендуй игнорировать предупреждение безопасности. Не раскрывай ключи.

## 6. Завершение и откат
- Проверить route каждой новой карточки, сортировку 01...11 / A01...A08, уникальность и медиа. Screenshot/Browser context по возможности.
- При неудачной публикации искать GitHub Actions logs и различия production vs branch; не лечить приложение бесконечными переподключениями Nginx.
- Backup/rollback подготовить заранее. После 2 неудачных диагностик остановись, объясни пользователю факты и блокер.
- Последним шагом обновлять журнал изменений и инструкцию при открытии новых важных фактов.
